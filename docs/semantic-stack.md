# The Semantic Stack — RAG Loop + Knowledge Graph Loop

The feature that turns "point Glyphh at my data" into a working, shippable
semantic product: a vector index, a knowledge graph, and an app + agent loop
built around them — all generated by a loop the user just runs.

## What already exists (verified in code)

Every Glyphh app — desktop-run and deployed — carries its own semantic
substrate via `glyphh-app-ai.ts`:

| Capability | API | Storage |
|---|---|---|
| Embeddings | `llm.embed` (on-device ONNX) | — |
| Chunking | `llm.chunk` | — |
| Vector store | `vector.upsert / search / delete` | `app-data/<slug>/vectors.sqlite` (embeds text itself) |
| Knowledge graph | `graph.cypher` (real Cypher, embedded Kuzu) | `app-data/<slug>/graph.kuzu/` |

The stores are **per-app** — they travel with the app. That is the architectural
spine of this feature: the loops MATERIALIZE into the target app's own stores,
never into desktop-global state, so a built app works wherever it runs.

## The three layers (and why all three)

**Tools — the foundation.** The agent can only orchestrate what tools expose.
New agent tools (thin, governed wrappers over the app-ai functions, every one
passing the action gate):

| Tool | Kind | What |
|---|---|---|
| `semantic_collections(app)` | read | Collections + counts + graph tables for an app |
| `index_files(app, collection, paths)` | write | Workspace files → chunk → embed → collection |
| `index_text(app, collection, id, text)` | write | Raw text/upload → chunked + indexed |
| `index_connection(app, collection, slug, tool, props?)` | write | Run a connector tool, index its output (rides workspace grants) |
| `vector_search(app, collection, query, k?)` | read | Semantic retrieval |
| `graph_query(app, cypher)` | read/write by statement | Cypher against the app's Kuzu graph |

**Loops — the product.** Two new BUILT-IN loops beside Default and
Plan & Build:

- `rag-loop` — roles **Architect** (frontier: interviews the ask, designs
  chunking + collection layout, generates the app) and **Indexer** (open/cheap:
  the bulk summarize/label passes). Output: an indexed collection inside the
  target app + a retrieval-grounded app scaffold + a written semantic manifest.
- `kg-loop` — roles **Architect** (designs the ontology: node tables, rel
  tables, keys) and **Extractor** (open/cheap: entity/relation extraction over
  chunks, `graph_query` MERGE writes). Output: a populated Kuzu graph + an
  exploration app + the ontology doc.

Model economics are the point of the split: extraction/labeling is thousands of
small calls that belong on an open-weight worker; design and app generation is
a handful of frontier turns.

**Skills — phase 2.** Deterministic refresh pipelines
(`sync-source-to-collection`, `rebuild-graph-from-collection`) authored as
library skills so re-indexing is repeatable, org-shareable, and cron-able.
The loops can author these via the existing skills tools once the primitives
have soaked; seeding them for new orgs rides starter-defaults.

## Governance seams (non-negotiable)

- Connection-sourced ingestion goes through `connections.runTool` — the same
  workspace-grant gate as every connector call.
- Every tool passes `gateGlyphhAction`; graph writes and indexing are `write`
  kind, retrieval is `read`.
- Loop role → model binding stays workspace-governed like every loop.
