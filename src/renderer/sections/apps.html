How apps use config vars

Config vars are per-app secrets: the key is visible below, the value is encrypted on this machine before it's stored and can never be viewed again — not here, not by the server. Delete and re-add a var to rotate it.

A Glyphh app that declares the secrets.get capability reads its own vars at runtime — e.g. an agentic app fetching the key it needs: 

await glyphh.call("secrets.get", { key: "OPENAI_API_KEY" })
// → { value: "sk-…" }   (only app code sees it, never the UI)

agent.run and llm.complete pick keys up automatically: a var named ANTHROPIC_API_KEY / OPENAI_API_KEY / GOOGLE_API_KEY powers that provider with no code at all. Keys belong to the app — Glyphh has no key store and makes no model calls of its own.

Exposing tools over MCP

Any agent — your own Claude, or someone else's — can add this app's /mcp URL as a connector and call the tools you approve. Everything runs on your machine, sandboxed by the Glyphh runtime; the app must be running (and your Glyphh client online) for calls to succeed.

Approval is an allowlist: a tool is unreachable until you switch it on, and any newly-appeared tool stays off until you approve it. Every call spends credits and is capped by the Guardrails limits.

Hard limits

These caps are enforced at the gateway before a call reaches your machine, so a runaway or abusive caller can't drain your credits or hammer your model. They apply to every app that exposes an MCP endpoint.

Per-call caps bound a single request; the window caps (tokens / calls) reset every window seconds; concurrency bounds simultaneous in-flight calls. Leave a field blank to impose no limit there.
